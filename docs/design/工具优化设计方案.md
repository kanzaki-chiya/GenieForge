# 帝国时代2决定版 Mod 工具优化 —— 可行性分析与设计方案

> 目标：解决 AGE 工具的三大痛点 —— ① 无增量修改（每次官方更新都要全量重做）② 无对比功能（两个 dat 差异要人工找）③ 无关联跳转（tech/效果全靠编号搜索）。
> 最终目的：**官方每次更新版本后，只需少量适配即可完成 mod 更新，而不是全量重做。**

## 二、现状分析：工具与文件格式

### 2.1 你手上的 AGE 工具是什么

`AdvancedGenieEditor3.exe`（9.8 MB，2025-08 构建）是一个 **原生 C/C++ 程序（PE32+，无 .NET CLR 头）**，属于经典的 Advanced Genie Editor（AGE）系列。附带文件：

- `AGE3NamesV0005/6/7.ini`：AGE 用来把「数字编号」翻译成「可读名称」的枚举表（护甲类型、地形表、文明资源 500 项等）。
- `openal32.dll`：音频运行库。

AGE 的定位是「dat / dll 全量读写编辑器」：**读入 → 改 → 存回**，没有增量、diff、关联跳转能力。

### 2.2 dat 文件格式（关键前提）

决定版的 `empires2_x2_p1.dat` 格式，实测确认如下：

1. **外层**：整文件是一段 **zlib 原始流（raw deflate，`wbits=-15`，无 zlib 头）**。解压后约 83.8 MB。
2. **内层**：解压后是 **Genie 引擎结构化格式**，头部是版本字符串 `VER 8.4`（或 `VER 7.8`、`VER 8.8` 等）。
3. 之后按固定顺序排列各数据段（section）：地形限制、玩家颜色、声音、图形、地形块、随机地图、**效果（effects）**、**单位头（unit_headers）**、**文明（civs）**、**科技（techs）**、科技树（tech_tree）等。

这个格式**完全公开、有成熟开源实现**，不是黑盒。

### 2.3 三大痛点的根因

| 痛点 | 根因 |
|------|------|
| ① 无增量修改 | AGE 只做「读-改-写」全量编辑。你的 mod 修改本质是**硬编码 ID** 的编辑结果（如「tech 22 金费改 30」），一旦官方更新插入新内容，**ID 整体漂移**，硬编码全部失效，只能在新版上重做。 |
| ② 无对比功能 | AGE 没有「读两个 dat → 对比」的流程，你只能靠人肉对照 `修改清单.txt`。 |
| ③ 无关联跳转 | tech → 效果、tech → 前置科技、文明 → 单位覆盖 等全是**数字 ID 引用**，AGE 只显示编号，不解析、不跳转、不反查，只能手动搜索。 |

> 实测佐证（VER 7.8 → 8.4）：科技 +297、效果 +237、新增 9 个文明，且有 4 个科技同名但 ID 漂移（如 `C-Bonus, Infantry Cost -20%` 从 344 → 731）。这就是「全量重做」的直接原因。

## 三、反编译可行性评估

**结论：不需要反编译，也不建议反编译。**

1. **AGE 本身开源**。原始项目 `Tapsa/AGE`（GitHub），社区还有 `kkpan11/Advanced-Genie-Editor` 等分支，源码可直接阅读，比反编译产物清晰得多。
2. **exe 是原生 C/C++（MFC/Win32）**，不是 .NET，无法用 dnSpy/ILSpy 直接反编译出可读源码；用 IDA/Ghidra 反汇编的工作量巨大、收益极低，还有版权风险。
3. **真正需要的是「dat 格式知识」**，而这部分早已被开源社区解决（见下节），完全不依赖 AGE 的实现。

> 因此，正确姿势是：**把 AGE 当「格式参考/对照工具」用，核心能力用开源库自建。**

## 四、数据模型（已实测确认）

### 4.1 顶层结构

```
DatFile
├── version            : str   (如 "VER 8.4")
├── terrain_restrictions / player_colours / sounds / graphics / ...
├── effects            : list[Effect]      # 全局效果表
├── unit_headers       : list[UnitHeaders] # 主单位表（1701 项）
├── civs               : list[Civ]         # 文明（含每文明单位覆盖）
├── techs              : list[Tech]        # 科技表
└── tech_tree          : TechTree          # 科技树连接关系
```

### 4.2 关键引用关系（痛点③「关联跳转」的数据基础）

```
Tech.effect_id                -> Effect (effects 表)         # 科技 -> 效果
Tech.required_techs[0..5]     -> Tech                        # 前置科技
Tech.resource_costs[0..2]     -> (type, amount, flag)        # 费用（金/木/肉/石）
Tech.civ                      -> Civ
Civ.tech_tree_id / team_bonus_id -> TechTree / Tech          # 文明 -> 科技树/团队加成
Civ.units[unit_id]            -> Unit (每文明单位覆盖)         # 文明 -> 单位属性覆盖
Civ.resources[0..600]         -> float                       # 文明资源（含各类效率/加成）
Effect.effect_commands[]      -> EffectCommand(type,a,b,c,d)  # 效果的具体指令
```

实测数据规模（VER 8.4）：54 文明、1278 科技、1218 效果、1701 单位头、15794 图形、760 声音。

你的核心修改（双倍文明特效、农田效率、贸易率、费用调整等）**全部能映射到这套结构**上，因此可以用「语义」而非「ID」去描述和定位。

## 五、解决方案设计

核心思想一句话：**把 mod 从「一堆硬编码 ID 的编辑结果」升级为「一份语义化补丁 + 一套 diff/索引工具」。**

### 5.1 痛点①：增量修改 → 「语义化补丁引擎」

**思路**：不再记录「改完的 dat」，而是记录「改了什么」的**补丁（patch）**，并用「名称/语义」定位目标，而不是原始 ID。

**补丁 DSL 示例**（YAML 或 JSON）：

```yaml
version: 1
# 每条补丁：定位目标 + 修改动作
patches:
  - target: { table: techs, name: "Loom" }          # 按名称定位，抗 ID 漂移
    set: { resource_costs[gold].amount: 30 }         # 织布机金费 50 -> 30

  - target: { table: civs, name: "Byzantine" }
    apply: "double_civ_bonus"                        # 自定义规则：该文明所有加成 ×2

  - target: { table: techs, name: "Banking" }
    set: { effect_multiplier: 1.1 }                  # 银行业贸易率 ×1.1
```

**每次官方更新的工作流**（这就是你要的「只改少量适配」）：

```
官方新 dat ──解析──> 新版对象模型
                        │
                        │  ① 自动匹配（见下）
                        ▼
                  应用补丁（set/multiply/规则）
                        │
                        │  ② 冲突报告（找不到/匹配多个 → 人工介入）
                        ▼
                  写回新 mod dat
```

**目标匹配三级策略**（解决 ID 漂移）：

1. **名称匹配**（首选）：`name == "Loom"`。绝大多数内容名称稳定。
2. **签名匹配**（名称变化/重名时）：用「效果指令集合 + 费用 + 前置科技集合」等结构特征做指纹匹配。
3. **相对位置匹配**（兜底）：在同一文明的科技树中的相对位置。

匹配失败/歧义 → 生成报告，人工只处理这几处，**而不是全量重做**。

### 5.2 痛点②：对比功能 → 「结构化 dat diff」

把两个 dat 解析成语义对象后，在**三个层次**做 diff：

| 层次 | 内容 | 用途 |
|------|------|------|
| 表级 | 各表数量变化（科技 +297、文明 +9、效果 +237） | 快速判断「这次更新动了哪块」 |
| 记录级 | 同名记录逐字段差异（Loom gold 50→30） | 精确看官方改了哪个值 |
| 引用级 | ID 漂移检测（`C-Bonus...` 344→731） | **直接定位你哪些 mod 需要适配** |

**两种典型用法**：
- **官方旧版 vs 官方新版**：看「官方改了什么」，据此判断自己的 mod 哪几条受影响。
- **官方版 vs 我的 mod 版**：自动生成/校验补丁，甚至反向从 diff 生成上面的 patch DSL。

### 5.3 痛点③：关联跳转 → 「引用关系图 + 反向索引」

构建全量引用索引，支持双向跳转：

- **正向**：Tech → 它的 Effect / 前置科技 / 所属文明。
- **反向**：Effect → 「哪些 Tech 引用它」；Unit → 「哪些文明/科技覆盖它」。
- **名称解析**：用 `lib/key-value-strings-utf8.txt`（语言表）＋ `AGE3NamesV0007.ini`（护甲/地形/文明资源枚举）把编号翻译成**中文可读名**，悬停显示、点击跳转、右键「谁引用了这个」。

这一层能直接消除「科技和效果靠编号人工搜索」的麻烦。

## 六、技术选型与架构

### 6.1 三条路线对比

| 路线 | 做法 | 评价 |
|------|------|------|
| A. 改造 AGE（C++/MFC） | 在 AGE 源码上加 diff/补丁/跳转 | 工作量大、MFC 门槛高、维护难，**不推荐** |
| B. 基于 genieutils-py 自建 Python CLI | 解析/写回/diff/补丁做成命令行 | **推荐起步**，见效最快，已验证可行 |
| C. Python 后端 + Web 前端 | 在 B 之上加可视化界面 | 进阶目标，体验最好，跳转/高亮最直观 |

**推荐路径：B → C 渐进式。**

### 6.2 关键技术事实（实测）

- 解析库：`genieutils-py`（PyPI，SiegeEngineers），专为决定版 `empires2_x2_p1.dat` 设计，支持 `GV_C20+`（FileVersion 7.7+，覆盖你的 7.8/8.4/8.8）。
- **必踩的坑（已定位并修复）**：`genieutils-py 0.1.2` 把 dat 字符串当 UTF-8 处理，但 dat 内部是**自定义单字节编码**，非 ASCII 字符串（如中文/特殊符号）读写会错位。需做 **3 处 latin-1 双向补丁**（见 `scripts/genie_poc.py` 的 `apply_string_fix()`），之后即可**字节级无损往返**（实测差异字节数 = 1）。
- 写回压缩用 `zlib.compress(..., wbits=-15)`，与官方压缩级别不同不影响游戏读取（游戏只认解压后内容）。

### 6.3 架构草图

```
┌─────────────────────────────────────────────────────────┐
│  CLI / Web UI                                          │
│   diff 视图 · 补丁编辑 · 关联跳转 · 冲突报告            │
└──────────────┬──────────────────────────────────────────┘
               │
┌──────────────▼──────────────────────────────────────────┐
│  核心层（Python，基于 genieutils-py）                    │
│  ① 解析/写回（含 latin-1 修复）                          │
│  ② 结构化 diff（表级/记录级/引用级）                     │
│  ③ 语义补丁引擎（定位 + set/multiply/规则 + 冲突报告）   │
│  ④ 引用索引（正向/反向跳转 + 名称解析）                  │
└──────────────┬──────────────────────────────────────────┘
               │
        genieutils-py（数据模型：techs/effects/civs/units/...）
```

## 八、风险与注意事项

1. **字符串编码**：latin-1 修复必须保留在代码里（否则写回损坏）。已在 PoC 固化。
2. **版本演进**：`VER 8.8` 与 `VER 8.4` 的 Tech 结构略有差异（多了一个 `research_location_count`），genieutils-py 已区分 `from_bytes_84/88` 处理，版本新增字段时要跟进库更新。
3. **效果指令 type 的语义映射**：`EffectCommand.type` 是数字枚举，需要维护一张「type → 含义」表（类似 `AGE3NamesV0007.ini`），否则 diff/规则可读性差。这是后续需要补的元数据。
4. **名称重名/名称变更**：少数科技名会重名（如各文明的 `C-Bonus...`），匹配策略要支持签名/位置兜底 + 人工确认。
5. **语言表与 dat 的对应**：dat 内的 `name` 是英文内部名，中文显示名在 `key-value-strings-utf8.txt`，关联跳转显示中文需要做一次 ID 映射（内部名 / language_dll_name 编号 → 语言表）。
